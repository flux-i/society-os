# Foundation decisions · 4 October 2026

The application is one Go process with explicit SQL and a same-origin React/Vite frontend. Built assets ship beside the binary in `build/web`; Node is needed for building, not for serving. No application LLM, payment gateway, bank integration or Tally runtime dependency is introduced.

SQLite uses pinned `modernc.org/sqlite` v1.60.1. Its pure-Go build avoids a C toolchain for the selected Linux targets. The actual embedded engine is measured in the CLI/API and baseline rather than inferred from a system SQLite installation. The driver brings its pinned `modernc.org/libc` dependency through its module graph. [Driver documentation](https://pkg.go.dev/modernc.org/sqlite).

Every connection receives WAL, FULL synchronization, foreign keys and a 5-second busy timeout through the driver's DSN parameters. The pool is limited to four connections. Startup rejects engines without a documented WAL-reset fix and mismatched settings. Tests reserve four simultaneous connections to verify setup. [SQLite WAL documentation](https://sqlite.org/wal.html).

Migrations ship in the Go binary, run transactionally and retain SHA-256 provenance. Current posted business records are not implemented yet. The registry uses unique flat identities, explicit resident relationships, membership intervals and separate finance-access flags, without treating a contact as an authenticated identity.

The server remains a local synthetic preview. It requires the fixture marker and demo flag and rejects non-loopback binds and untrusted Host values. Schema 2 added password sessions, time-bounded roles, scopes, registry mutations and immutable audit. Schema 3 adds invitation/assisted password recovery, required privileged TOTP, hashed recovery codes and fresh identity checks. Real identity/custody and subsequent role/account administration remain production gates.

Passwords use pinned `golang.org/x/crypto` v0.57.0 Argon2id with 64 MiB, three passes and two lanes; calibrate against production hardware before deployment. The HTTP layer permits at most two simultaneous password checks and bounds/throttles login attempts. Session tokens have 256 random bits and are stored by SHA-256 hash; CSRF tokens are separate random values. Cookies are HttpOnly/SameSite Strict. Secure cookies apply under TLS; the current CLI permits only loopback HTTP. [Go Argon2 documentation](https://pkg.go.dev/golang.org/x/crypto/argon2), [OWASP password storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html).

Sessions have 30-minute idle and 8-hour absolute limits. Background identity checks do not extend idle lifetime. Role expiry/revocation, account/auth-version changes and current membership scope are rechecked per request. Origin and synchronizer-token checks protect writes. Registry edits reserve the SQLite writer before permission reads, compare the home version and commit the mutation/audit atomically. A rejected edit leaves no record, version or audit side effect. [OWASP sessions](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [OWASP CSRF prevention](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

The demo administrator can manage registry records, while committee/treasurer grants provide operational registry reads. Administrators can invite current registry people and issue password-reset links after fresh verification. Financial posting and subsequent role/account administration are not implemented. Residents receive only homes with a currently active membership and only current people in those homes; staff can inspect historical relationships. Finance access requires a separate permission/entitlement policy when that workflow is added.

The local recovery command uses `VACUUM INTO`, removes sessions, access links and recovery codes from the private copy, validates integrity/foreign keys/migration provenance and writes a versioned manifest. Restore requires a fresh destination and verifies copied bytes and counts. Identity/audit and confirmed encrypted factors survive; temporary credentials cannot revive. Preserve the matching MFA key separately. Encryption, S3 snapshots, recovery keys, current-access reconciliation, external effects/numbering and custodian-held recovery remain separate production requirements.

Frontend dependencies are exact versions with a lockfile. Tailwind's build-time styling and locally packaged fonts provide the visual foundation. The PWA manifest defines the app shell identity; no service worker stores personal API responses. [Vite documentation](https://vite.dev/guide/).

MFA uses RFC 6238 TOTP, consumed-step replay protection and a persistent five-attempt/15-minute budget. AES-256-GCM binds encrypted factors to their user. The private key is outside snapshots; missing/wrong keys fail startup/readiness. Browser-generated QR codes remain local. Password reset preserves factors and revokes sessions. Lost-factor recovery is an offline two-custodian attestation command, with no web disable/reset endpoint. [Account-security acceptance and boundaries](account-security-baseline.md).

Invitation/reset links are random, hashed, expiring, single-use and authentication-version-bound. Manual identity/email attestation precedes issuance and handover. Admin/committee roles have bounded terms. Sensitive actions require confirmation within five minutes. The four public demo accounts alone have a synthetic MFA exploration helper; invited accounts do not. Production use stays disabled.
