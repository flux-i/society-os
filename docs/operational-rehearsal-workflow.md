Stable source identities come from the independently supplied 118-home register. Registry import continues to grant no financial entitlement.

## Codebase reality and required decisions

`flat_memberships.can_view_finances` already scopes personal ledger, maintenance, collections, fine, document and export reads. `principalScope` includes that flag, so changing it can invalidate private screens and held native results. Current registry creation implicitly enables it for a new owner, while the initial import correctly leaves it disabled. There is no ordinary control for deliberately granting financial visibility to an imported household. Implement an explicit Treasury-owned visibility workflow; a registry officer's power to maintain people is insufficient to grant it.

`ReceiptSnapshot` and the PDF renderer preserve originals, but the renderer currently prints a fixed fictional/local-preview heading. Inspect the snapshot creation and rendering paths before implementation. New configured-workspace receipts must retain the supplied workspace identity and explicit fictional-rehearsal marker in their frozen source. Existing receipt snapshots and PDFs must keep their original identity; no retrospective relabelling or invented statutory fields is allowed.

Actual society identities, approved receipt/finance policy, custodian choices, production host/network and external credentials are unavailable. They block their dependent activation and representative acceptance, not this fictional development/rehearsal. Preserve the existing demo preview and every accepted archive.

## Implementation decisions after the accepted setup checkpoint

The published setup/import application is `9429972344239778a57eac5777f59975f8a04e30`, with metadata child `d2b321dfb0897f673dee33276fbe3b30ce019d12`. Preserve its paired preview and immutable 507-source/820-hash archive while this workflow is built.

Financial visibility is a separate Treasury-only home tab and endpoint. It applies to a person across all of their current relationships in the selected home, so revoking one role cannot silently leave a second relationship granting the same household access. Historical and other-home relationships remain untouched. An explicit grant/revoke uses the current home version, a confirmed verification note and stable operation identity. Current fresh Treasury authority is checked before replay; accepted replies are retained without reapplying an old grant after a later revocation. A new immutable schema-26 action table retains the supplied request digest, original result and linked audit. New registry memberships start with financial visibility withheld; existing accepted grants and demo data remain preserved. A Treasury operator cannot grant personal household access to their own linked person; another current operator can perform that verified grant. Staff appointments continue to control their separate staff access.

New configured-workspace receipts receive an optional versioned issuer object containing the supplied society name and workspace mode at confirmation. Rendering reads that frozen object, with an explicit fictional-rehearsal marker. Legacy snapshots without the object use the original renderer branch and preserve their original identity/format. No statutory address, registration or policy fields are invented. Verify the actual PDF and original/correction/restore behaviour.

The 12-home source is A-101 through A-304 from the supplied register: A-204 is vacant; A-103, A-202, A-301 and A-304 are rented. Independent expectations are 11 occupied/1 vacant, 12 distinct current owners, 4 current tenants, 17 people and 18 relationships. Staff and residents are established through visible bootstrap/import/invitation/appointment/MFA controls. Database reads may independently verify results; direct permission updates must not make the rehearsal pass.
