## Planned retained protocol

Append schema 31 with separate immutable numbering-policy and decision records plus encrypted series intents and append-only handoff events. Preserve every existing row, BLOB and SQL object; old review kinds/decisions are not rewritten. Policies have explicit source/appointment/author binding, linked version, supplied prefix, digit width, first/last sequence, period/authority evidence and private namespace reference. Use technical bounded ASCII formats and exact safe integers; expose the bounds and independent example without silently inventing a fiscal/statutory format.

A different current freshly authenticated reviewer approves or declines the exact frozen policy with an explicit reason/attestation. Self-review, copied/expired/revoked nominees, stale versions, changed content and conflicting concurrent decisions fail without effects. Exact lost-response retries return one retained result. Decisions establish preparation only.

An offline reservation command reads explicit bounded private input/configuration files on an existing matching restored database. It requires an approved current policy, exact source/appointment, stable operation identity and two independent supplied custodian attestations about the namespace and evidence. Public recipients encrypt the exact canonical reservation manifest. Persist the one original encrypted BLOB/checksum and intent atomically before external handoff, so restart or a lost command reply cannot produce a new ciphertext or silently change the request. Storage credentials/private custody keys never reach the resident HTTP routes, SQLite records, logs or stdout.

Before the one initial `PUT`, append a durable handoff identity. Preserve separately known rejection, unresolved handoff and verified checksum/version states. Response loss, conflict, 5xx or incomplete acknowledgement stays unresolved; it does not establish a reservation or permit a new `PUT`. An identical command retry returns retained state/ciphertext. Deliberate bounded retry after a known rejection must name the retained intent and a fresh exact attempt; it cannot retry uncertainty or reseal data. A crash after handoff recording remains uncertain even if the network call may not have happened.

An offline reconciliation command uses a separately configured retrieval principal, an independently supplied exact non-null version, and private custody identities. It verifies the retrieved original ciphertext checksum/length, decrypts its bounded manifest, and compares the exact retained source/policy/operation/society/namespace before appending verification. It cannot adopt another host's conflicting reservation, trust a guessed ETag, upload new bytes, replace an object or manufacture an acknowledgement. A late genuine acknowledgement may be retained historically after a nomination changes, but it cannot make that earlier appointment/policy current again.

The portal shows bounded policy/history and reservation progress to current recovery reviewers only. Opened selections, hover/focus/keyboard, pending/uncertain inputs, internally scrolling dialogs, meaningful empty/loading/error/retry states and separate approved/declined/stale statuses follow the verified shared review controls. Current scope/epoch/appointment changes discard stale results; unchanged status reads preserve forms. Actual native WebMCP may read bounded numbering/preparation status only; it cannot approve, reserve, retrieve custody material, issue receipts or release recovery.
